# Retro Messenger — Windows automatic updates (v1.1.1)

This project integrates the **official signed Tauri 2 updater**. It checks for updates at startup in installed Windows releases and in **Messenger Options → Updates**. Updates are downloaded only after the user chooses **Download & install**. The client checks the installer's Tauri signature before installing it.

**You still own the signing key and GitHub repository.** This source package deliberately does **not** contain a private key or a published release. A secure updater cannot be enabled for your users without those two things.

## 0. Requirements

- Windows 10/11 with Node.js, Rust **1.90+**, WebView2 and NSIS prerequisites for Tauri 2.
- A **public** GitHub repository to host downloadable GitHub Release files. (If you want closed source, keep the source separate from the public releases repository; extra publishing credentials would be needed.)
- Supabase URL and publishable key for desktop builds. Never use Supabase's service-role or secret key in frontend variables.
- Keep the same app identifier `app.retromessenger.client` and preserve signing keys across updates.

## 1. Extract and install dependencies

Unzip the project into `C:\Users\gusfa\Documents\retro-messenger` (or your chosen directory) and **preserve your existing `.env`**.

In PowerShell:

```powershell
cd C:\Users\gusfa\Documents\retro-messenger
npm install
rustc --version
```

If your Rust version is below 1.90, run `rustup update stable`.

## 2. Generate your personal signing key and configure the release URL

Create (or select) your public GitHub repository, for example `YOUR_GITHUB_ACCOUNT/retro-messenger`.

On **your own Windows PC**, run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-updater.ps1 -Repository "YOUR_GITHUB_ACCOUNT/retro-messenger"
npm run updater:verify
```

The script:

1. Generates a signing key and `.pub` file in `%USERPROFILE%\.tauri\` **only if no key exists**.
2. Reads the **public** key and inserts it into `src-tauri/tauri.conf.json`.
3. Changes the update endpoint to `https://github.com/YOUR_GITHUB_ACCOUNT/retro-messenger/releases/latest/download/latest.json`.
4. Preserves the private key; never embeds it in project source.

**VERY IMPORTANT:** Back up `%USERPROFILE%\.tauri\retro-messenger.key` and the key password securely. Losing them means you cannot ship updates trusted by already-installed clients. Do not email the private key or paste it into chat. **Never generate a different key on a whim** after releasing the app.

The sample configuration intentionally has a placeholder public key until this step. For that reason, do not build or distribute the installer before setup.

### Note: the signing key file uses Base64

The `.key.pub` file generated by Tauri 2 stores a **Base64-encoded Minisign public key**. The setup and verification scripts decode it for validation, but insert the *original Base64 string* into `plugins.updater.pubkey`. You do not need to regenerate keys if an older script incorrectly complained about the missing `untrusted comment:` text. This validation was fixed in the updated v1.1.1 source package.

## 3. Prepare GitHub Actions secrets

Push the configured project (which includes the **public** key and release URL, never your private key) to your GitHub repository.

In that repository, open **Settings → Secrets and variables → Actions → New repository secret** and add:

| Secret | What to put in it |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | The **full text** of your local `.tauri\retro-messenger.key`, copied securely into the secret form. Never commit it. |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | The password you selected during key generation; empty if none. |
| `VITE_SUPABASE_URL` | Your production Supabase HTTPS project URL. |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Your **publishable / anon** Supabase key, never a service-role key. |

The GitHub Actions workflow uses GitHub's automatically supplied `GITHUB_TOKEN` to create a release and upload files; set **Repository Settings → Actions → General → Workflow permissions** to allow workflows appropriate write access if your organisation restricts it.

If you choose to keep your source repository **private**, GitHub's assets will not be anonymously downloadable. For a public updater with private source, use a separate public releases repository and a credentialled publish workflow, or a public HTTPS CDN. The bundled workflow targets a public source/release repository by default.

## 4. Publish a signed release

Bump `package.json` version, `src-tauri/Cargo.toml` version and `src-tauri/tauri.conf.json` version **together** for future releases (this package starts at `1.1.1`). Commit and push the changes.

Open **GitHub → Actions → Build signed Retro Messenger for Windows → Run workflow**. The workflow builds the customised NSIS installer, signs it, generates `latest.json`, and uploads the files to a **draft** GitHub Release.

Review the draft release, download/test the installer on a clean Windows machine, then click **Publish release**. A draft does not appear at the `/releases/latest/download/latest.json` endpoint.

Example files created:

- `Retro Messenger_1.1.1_x64-setup.exe` — Windows installer (exact name may differ).
- `...setup.exe.sig` — cryptographic signature for the update.
- `latest.json` — updater manifest with version, verified artifact URL and embedded signature.

The workflow uses `tauri-apps/tauri-action@v1`. The action generates `latest.json` automatically; you should **not** hand-edit its signature field.

### Local signed NSIS build (optional)

If you prefer to build on your Windows PC:

```powershell
npm run desktop:build:signed
```

This script reads your locally stored signing key, asks for the key password without echoing it and produces an installer and `.sig`. **A local build alone does not publish an update**. Use GitHub Actions to publish a complete signed release, or upload a matching `latest.json` yourself.

## 5. Test the updater

1. Install your **first** release with the updater embedded (for example `1.1.1`).
2. Create a later release by bumping all three versions to `1.1.2` and running the GitHub workflow again. Publish it.
3. Open the installed `1.1.1` app. After ~5 seconds, it should offer `1.1.2`. Or open **Messenger Options → Updates → Check for updates**.
4. Confirm the version and release notes. Click **Download & install**. The signature must match the public key embedded in `1.1.1`.
5. Verify the installed app reports `1.1.2` after updating.

The website deploys separately through Vercel. The updater runs only in packaged **Windows releases**, not inside `desktop:dev` or the browser. Older installers **without** the updater require a one-time manual installation of an updater-enabled release.

## Security notes / troubleshooting

- Never disable signature verification or publish a release signed with an unrelated private key.
- The updater signing key is **not** a Windows Authenticode code-signing certificate; unsigned installers may still trigger SmartScreen.
- On Windows Tauri can close the app during installation; test with open conversations to ensure client state is saved normally.
- Release not found / 404: publish the draft, confirm the repository is public, confirm `latest.json` was attached, and check the endpoint in `tauri.conf.json`.
- Invalid signature: ensure you use the SAME signing key for all releases; do not regenerate it.
- `npm run desktop:dev` may build without release signing environment; only a production update artifact needs signing credentials.
- To release from GitHub Actions, keep `.env` private and configure the four GitHub secrets. Do not commit `.env`.
